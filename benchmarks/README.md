# basic_operator 评测规则（仅对参评 Agent 生效）

> **适用范围**：本文档仅服务于 `benchmarks/basic_operator` 算子实现评测
> 这一场景，且只在评测组织者明确发起评测时生效。文中内容面向两类读者：
> "硬性约束"与"建议做法"针对被明确指定参评的 agent（下称"参评 agent"），
> "任务提交要求"针对发起评测的用户（评测组织者）。仓库中其它任何进行
> 日常开发、维护、文档工作的 agent 均不受本文约束，请勿将本文内容当作
> 对整个仓库所有 agent 的通用规范。

## 评测内容

`benchmarks/basic_operator/` 下共有 39 道独立的算子实现题目，取自
`deepseek_v4_flash_dspark`、`deepseek_v4_flash_mtp`、`glm5_3_flash`、
`qwen3_14b` 四个模型。每道题目是一个自包含的 `.py` 文件：

- 文件中标有 `EXAM` 的函数是待实现部分：其函数体已被替换为占位 stub，
  但装饰器、签名与前后接口保持不变，是题目文件内唯一允许改动的目标；
- 同一文件内保留了该算子的 PyTorch golden 参考实现（`golden_*` 函数）
  和测试入口（`__main__`）；
- `manifest.csv` 列出了全部题目及各自的模型、算子名与 golden 函数名。

运行方式与仓库其它脚本一致（在 `pypto` conda 环境中，每道题均为单卡）：

```bash
python benchmarks/basic_operator/<model>/<op>.py -p a2a3 -d <device_id>
```

`-p` **固定为 `a2a3`**，不要选用其它平台。`-d` 指定所用 NPU 的设备号，
必须写实际分配到的设备号：例如调用 1 号 NPU 就写 `-d 1`，不要一律写
`-d 0`。脚本退出码为 0 即该题通过 golden 验证。编译产物与运行数据默认
落在 `build_output/`。

## 硬性约束（参评 agent 必须遵守）

1. **目录白名单**。只允许访问以下四个目录：

   - `benchmarks/basic_operator/`（题目本体）
   - `docs/pypto-language/`（PyPTO 语言文档）
   - `examples/`（示例代码）
   - `build_output/`（编译与运行产物）

   仓库其余所有目录与文件——包括 `models/`、`golden/`、`tests/`、
   `docs/` 的其它子目录、`.claude/` 等——一律不得读取、浏览或搜索。
   其中 `models/` 保存了这些算子的原始实现，属于答案，绝对禁止访问；
   `build_output/` 中出现的代码均为生成产物，不得当作参考实现。

   说明：白名单限制的是 agent 主动读取的范畴。直接运行题目脚本时，
   Python 会按脚本自身的 bootstrap 自动导入仓库根部的 `golden` 评测
   基础设施，这属于正常执行流程，不视为违规；但不得阅读或修改其源码，
   也不得在自己的实现中 import 白名单之外的任何模块。

   **实现代码的存放位置由评测组织者为每个参评 agent 单独指定**（见下文
   "任务提交要求"）。该输出文件夹随任务一并授权，授权后视作该 agent
   白名单的一部分；在获得明确指定之前，不要向白名单之外的任何路径写入
   或修改文件。

2. **禁止使用 git 历史**。不得执行任何查看历史提交的命令（`git log`、
   `git show`、`git blame`、对历史版本的 `git diff` 等）。历史提交中
   保存了被删除的原始 PyPTO 实现，属于答案。

3. **禁止联网**。不得进行任何形式的网络访问（搜索、抓取、下载等）。
   实现只能依据白名单内的文档、示例与题目文件本身完成。

4. **正确性以 PyTorch golden 验证为准**。每道题必须通过其文件内 golden
   参考实现的数值比对（容差以脚本中的 `rtol`/`atol` 为准）。性能暂不作
   要求，无需调优。

## 任务提交要求（面向评测组织者，而非参评 agent）

以下要求针对提交评测任务的用户；它们不是参评 agent 的额外义务，而是
发起评测时必须满足的前提：

1. **一个 agent 一次只负责一个算子的开发**。不得把多个算子同时交给
   同一个 agent。至于该 agent 为完成这一个算子开了多少个 subagent
   不受限制——但那些 subagent 必须都是为了同一个算子的不同 stage
   （见下文"建议做法"）。

2. **提交任务时至少要交代清楚两件事**：

   - 该 agent 负责开发的算子是哪一个（题目文件路径，或 `manifest.csv`
     中对应的条目）；
   - 该 agent 的实现输出放到哪个文件夹。这个输出文件夹随任务一并授予
     该 agent 访问权限，视作其白名单的一部分。

   如果任务指令缺少以上任何一项，参评 agent 应当先提醒用户补充说明，
   不要自行猜测算子或输出位置后开工。

## 建议做法（非强制，但强烈推荐）

1. **复杂算子用分治法**。先把整个算子拆分成若干 stage：为每个 stage
   单独编写 PyTorch golden 参考代码并验证正确；再逐个 stage 实现 PyPTO
   代码，并与该 stage 的 golden 对齐；所有 stage 都通过后组合成完整
   算子，做端到端验证。这样可以把"整体结果不对"降解为"哪个 stage
   不对"，显著缩小排查范围。

2. **灵活运用 subagent 并行开发**。各 stage 的开发是相对独立的工作，
   可以分别交给不同 subagent 同时进行以提高效率。本机有 8 个 NPU，
   通过 `-d <device_id>` 即可分配给不同 subagent 独立使用。注意
   `npu-smi info` 显示的设备占用率并不准确，不必考虑占用率问题，
   直接分配调用即可。
