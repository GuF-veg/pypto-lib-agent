# pfdb 后续开发计划：用优化实验决定接口与信息取舍

日期：2026-10-21。状态：**本轮实施已闭环，未证实总体优化收益**；结果、未评估项与偏离协议见[开发与实验记录](pfdb-development-results.md)。本文保留原验收依据；未选假设仍需各自证据，不因完成本轮实验就批准删除接口。

2026-10-22 扩展：已用 OpenCode Go 的 DeepSeek Flash 对五道新题开展生成、修订、真机验证及既有工件回放；见[新算子研究](pfdb-new-operator-study.md)。其第 8 节更新了后续优先级，仍未提供删除 PMU、memory 或 scheduler 能力的充分依据。0.7 的增量实现、后续 24 次目录对照、12 次语义对照及 0.8 的权限目录/事实范围实现见[接口实施与验证](pfdb-native-interface-results.md)。

本计划承接[面向算子 Agent 的反馈研究](pfdb-agent-feedback-research.md)，从 SWA 与 compressor_ratio4 两次实践出发，安排后续实验、开发顺序与验收标准。最初交付仅为计划文档；后续实施授权后，实验与实现单独记账，保留本文的完整目标和验收条件。

## 1. 要回答的问题与最终交付

目标不是让 pfdb 提供最多指标、最少工具，或固定成某三个入口，而是让算子开发 agent 在给定预算内，**更可靠地得到有用证据，提出合法且可检验的改动，最终获得通过验证的完整算子性能收益**。

后续工作必须回答四个问题：

1. 哪些现有接口的区分对 agent 没有帮助，可以合并、改为按需发现或弃用？
2. 哪些信息只是默认展示过多，底层能力仍必须保留？
3. 哪些困难来自访问缺陷、缺少关联或文档口径，哪些确实需要新增数据？
4. 增加或减少这些信息，是否改变了正确决策与真实优化结果，而非只改变响应长度？

最终交付应包含：可复用的实验集、逐项能力/接口决策台账、经评测选择的默认访问方式、必要的增量实现、兼容迁移与 runtime 升级验证。允许结果是“某项不值得做”或“证据不足，继续保留”。

实施边界保持不变：

- pfdb 只读取已有工件；新的编译、golden、设备运行、PMU 或模拟器采集由外部执行器负责。
- 不修改 PyPTO、runtime 或原始采集。复用 runtime 官方分析口径；缺陷只在 pfdb 一侧做窄兼容，并记录版本、复现、测试和退役条件。
- query 提供事实、来源与不确定性，不替 agent 宣布瓶颈或接受候选。实验的测量结果与 caller verdict 分开。
- 公开工具层可以集中清理；底层能力、历史数据库与旧调用方的迁移须可验证，不能用“简化”掩盖证据丢失。

## 2. 从实践得到的起点，而非预设答案

当前代码锚点为 pypto-lib `d6cbf967bcf0d4b4bc412467cf28c944e26b1362`，pfdb 0.4.0 / DB schema 8 / MCP schema 4。研究时有 27 个注册 query、41 个 MCP tools，其中 8 个写操作。执行计划前重新记录真实版本与客户端实际发现的工具，不能把这些数量当作永久基线。

| 实践事实 | 后续应检验的系统假设 | 不能预设的结论 |
| --- | --- | --- |
| SWA 合并提交后 274.5→250.4 µs，物理行数不变 | 显式 submit/grid/block 关系比笼统并行度更有用 | 删除 density，或增加 blocks 必然无用 |
| SWA 缩窄组依赖有收益；无实际流水的拆分反而变慢 | 完成边界、region 与实际重叠帮助选择合法粒度 | 依赖越少越好，任务越细越好 |
| 两例都有特定 RoPE scatter/gather 的有效对照 | task→generated primitive→具体 form 的关联有价值 | 所有 scatter 都应该替换 |
| compressor agent 在已测 fixture 上整体胜出，投影却较慢 | 跨实现阶段对应与完整 latency 可以纠正局部排序误判 | 手写是答案，或融合收益已被单独量化 |
| scan-8 显著获益，但有 position/mapping 前提 | workload/validation 契约能阻止不合法的“胜利” | 当前 PASS 足以证明通用正确性 |
| 长序列 projection task 跨度远大于最长 row | row 分布、启动展开与 chunk 映射能减少错误解释 | task span 就是单个 matmul 纯计算时间 |
| MCP 截断续取和 `tasks --name` 有已复现缺陷 | 一部分问题只是已有证据拿不到 | 修复入口就证明 agent 优化能力提高 |

完整数字、控制条件和局限以 [SWA 研究](../../benchmarks/implementation/deepseek-v4.1-flash/performance-gap-study.md)、[compressor 研究](../../benchmarks/implementation/deepseek-v4.1-flash/compressor-ratio4-performance-gap-study.md)和[综合研究](pfdb-agent-feedback-research.md)为准。不把历史的 23 组配置当作 23 个独立算子样本。

## 3. 怎样判定“冗余”和“不足”

### 3.1 将三种删除决定分开

| 层次 | 冗余的候选判据 | 可能的处理 | 删除前必须证明 |
| --- | --- | --- | --- |
| 默认工具目录 | 多个入口使同一工作流难以发现；按需发现能完成相同任务 | 隐藏维护工具、分组发现、入口收敛 | 低频场景仍有明确入口，发现成本没有反向增加 |
| 默认响应 | 重复上下文、大量 rounds/rows/counters 不改变当前判断 | 摘要先行、过滤、分页、明细后置 | 关键证据完整可达，摘要没有漏掉尾部或反例 |
| 底层功能/实现 | 同一权威问题已有等价能力，且没有独立用户价值 | 复用同一 handler/上游入口；弃用重复实现 | 语义、来源、边界、失败行为与升级测试一致 |

“两个接口都含时间字段”不等于冗余；CP、row 生命周期、PMU busy 和无插桩 bench 回答不同问题。CLI/MCP 共用 handler 是合理复用，不因存在两种通道就删除其中一个。别名的兼容收益也可能大于其维护成本。

“两例没用过”不构成删除依据。host、scope、args、incore、多 rank、冷启动等能力，须由专门场景检验；没有场景时标为**未评估**，保留按需入口。

### 3.2 对每个困难先做归类

统一记录为：**未采集、未导入、未绑定、未派生、展示/发现困难、接口错误、解释错误、变换/验证失败**。

例如：独立 PMU-only capture 已在磁盘但未绑定，不是缺 counter；row 数据完整却默认截断，不是缺 block timing；已给出 mechanism 但 agent 仍写出错误变换，不应立即扩张 pfdb schema。

## 4. 工作流与接口盘点：先建立台账

盘点单位为“问题—能力—view/参数—通道”，不是只数顶层命令。每项至少记录：owner question、输入工件、handler/runtime 来源、默认响应、完整证据入口、调用者、权限、成本、测试、候选替代、当前决定与证据。

| 现有能力组 | 本轮重点研究什么 | 初始处理假设，均待实验 |
| --- | --- | --- |
| `runs_list / overview / inventory / bench` | 定位 run、比较条件、缺失工件与目标数字是否分散；raw rounds 是否默认过多 | 候选统一首层摘要，保留 inventory/bench 明细 |
| `density / sparse_regions / region / why_sparse / core / idle_window` | 哪些问题必须用时间窗口；哪些默认导航步骤多余 | 按问题发现，避免要求每次从密度逐层下降 |
| `tasks / task / why_long / rows` | 定位与逐实例列举是否重复；是否缺 launch spread 与分布摘要 | 共享 selector；局部摘要后钻取 rows |
| `deps / subgraph / critical_path / why_late / early_dispatch / scheduler` | 结构、路径、调度是否被混为因果解释；哪些 view 应局部组合 | 共用对象/窗口关联，保留各自权威定义 |
| `pmu / perf_hints / memory / incore / args_dump` | 数据已经存在但无法关联，还是确实缺 artifact；完整输出如何续取 | 目标 kernel 的局部联合视图，原始明细按需 |
| `host / scope_stats / render` 与导出 | 两例未覆盖的 host/容量/生命周期问题、图像/文件证据是否能独立帮助判断 | 暂不删能力；补专门正向用例；render 属于开发分析 |
| `compare / baseline / trial / note` | 目标口径、输入有效性、实验记忆、prune 后记录是否足够 | 增强契约和条件化结果，避免先重建搜索系统 |
| `attach / refresh / version` 等维护与兼容操作 | 与开发 agent 的只读任务混列是否增加发现成本 | 默认目录与维护目录分离候选，能力保留 |

实现来源以[注册表](../../profile_db/src/profile_db/query/registry.py)、[参数](../../profile_db/src/profile_db/query/params.py)、[MCP 工具构建](../../profile_db/src/profile_db/mcp_server.py)与[公开手册](profile-db.md)为准。字段存在与 agent 能正确利用，必须分开记录。

最终决策使用六种状态：**保留默认、保留按需、合并呈现、修复、增补、弃用/删除**；允许“未评估”。每个状态必须附适用场景、替代路径、反例和复审触发条件，不能给所有接口一个脱离场景的总分。

## 5. 实验基础：工件集、答案隔离与记录

### 5.1 最小工件集

先整理现有数据，不先重新采集。以 SWA 和 compressor 各自的 agent/手写起点、关键有效干预、无收益/回退干预和无效候选构成开发集。逐项验证源码/产物、bench、swimlane、PMU、validation 的关联。

研究报告、CSV 和图片不是完整 capture 的替代品。若原始工件丢失或旧数据库没有有效 run，记录缺口；能用现有完整工件重建临时数据库则重建，确需补采则交给外部执行器。不得从报告答案制造“原始事实”。

工件 manifest 至少包含：

- case/workload/实现身份、源码与编译产物 digest、平台、工具链 pin；
- 输入/合法域、reference、comparator、validation coverage；
- 各 capture 的类型、计时域、采集配置、hash、身份关联与缺失原因；
- 不插桩 bench 的 estimator、rounds/warmup、strata、原始样本；
- 每个实验条件允许访问的证据清单及其 digest。

大型原始工件留在现有忽略目录或受管理的工件存储；公开仓库只存可公开的小 manifest、缩减 fixture、脚本和结论，不提交 `build_output/`。原库、原 capture 不变，评测使用独立工作副本。

### 5.2 两套答案与权限

为同一题准备 agent 可见材料与评审专用材料。评审材料可以引用历史干预结果，agent 材料不能包含已知修复代码、收益数字、报告结论或带答案的文件名。golden/reference 固定，不因某个候选失败而改宽容差。

离线题限制在声明的证据空间内，避免 agent 通过任意文件读取找到研究报告。在线优化允许什么源码、DSL 文档和手写参考，须对两组完全一致；默认将“手写参考可见/不可见”作为分开的条件，不混报。

观测日志记录工具发现、输入/响应、错误与恢复、可见字节/token、代码 diff、公开假设、实验及验证。**不依赖模型隐藏推理**。真实调用轨迹由评测执行器记录，先不为此建设新的数据库子系统。

## 6. 实验 E0：先排除访问缺陷的干扰

保留原样 A0 作为历史可用性基线；建立只修传输问题的 A1，后续主实验以 A1 为共同基础。A1 不新增 workload 契约、PMU 关联或优化建议，避免把新增信息混入“修 bug”。

最小任务是修复并通过公开入口验证：`tasks --name` 参数碰撞、MCP 截断后的可执行续取、异常的结构化返回。复用现有 handler；分页或预算方案先用大 rows/hints/path 和边界输入验证，不在本文提前锁定。

验收要求：

- API/CLI/MCP 的同一 selector 返回等价事实；已知 name 查询能从公开路径成功。
- 完整续取与无限制参考结果逐项一致，无重复/遗漏；捕获/analysis 变化后不能继续使用失效定位。
- 空结果、缺失工件、非法 selector、错误 rank、不可用 runtime 分析都有可操作的结构化状态。
- 只读访问没有写入数据库；原工件 hash 不变；原有测试与相关真实工件回归通过。

E0 是确定性正确性工作，不必等 agent 性能显著提升才修。A0→A1 可测错误率和恢复成本，但收益不归给新的信息设计。

## 7. 实验 E1：发现方式与展示方式是否冗余

先固定证据集合、分析算法、权限和文档，分别做两个小实验，不一次改整个接口栈。

| 对照 | 唯一改变 | 检验问题 |
| --- | --- | --- |
| 平铺目录 vs 按工作流分组/按需发现 | 工具的发现与默认暴露方式 | 维护/低频工具是否干扰主要任务；按需发现是否导致漏能力 |
| 现有 fact 列表 vs 有界关联摘要＋明细入口 | 响应组织；完整证据与访问权相同 | 摘要是否减少误判和无效调用；是否隐藏反例 |

纯表达对照必须保持语义事实集合一致，包括字段值、单位、scope、来源和已知关系；只改变分组、顺序、默认详略与展示。新增 launch spread、统计量或此前未提供的映射，进入 E2 的派生信息条件；不能借“摘要”额外引入新判据。

“brief / inspect / compare”可以做原型，但不是预定赢家。与更小的调整对照：修复原工具说明、统一 selector、保留旧工具但减少默认目录。记录真实客户端实际加载的 schema/token，不能把全部 schema 文件大小等同于 prompt 成本。

优先使用第 8 节的 10 道离线题。每个选定对照先做 **10 题 × 3 个匹配 seed × 2 条件 = 60 次尝试**的预试；若必须检验发现方式与响应方式的交互，再做 2×2，避免默认穷举所有界面组合。

探索性筛选可复用同一批 30 次 A1 记录：基线加发现、表达、信息、记忆四个单因素条件合计 150 次，而非四次重复跑基线。比较因此相关，且选赢家有选择偏差；确认阶段必须冻结方案，使用未见材料和新的独立会话，不能把筛选最好结果当成确认收益。

信息压缩的确定性检查与 agent 表现同时进行：摘要是否保持单位、scope、来源、缺失/截断状态；每个证据 handle 是否可取；极值 row 和稀有 hint 是否仍能找到。简单页数减少不能覆盖这些失败。

## 8. 实验 E2：究竟缺什么信息

### 8.1 用两条轴拆开“更多信息”和“更好的表达”

|  | P0：逐项 facts/现有形式 | P1：有关联的有界摘要 |
| --- | --- | --- |
| D0：当前允许的证据 | 修复后基线 | 只验证表达与检索收益 |
| D1：补充声明的证据 | 验证补充证据能否被自行利用 | 验证补充证据与表达的联合效果 |

D1 每次只加入一类缺口。先用离线外部证据包做原型，不要求先迁移 schema。固定材料可手工标注，但只能给来源清楚的事实，不能把调优结论包装成“proven”。

严格区分三类变化：原始证据新增、现有证据的确定性派生、现有证据的索引/展示。如果源码本来就在 D0 的访问权限内，新增 task→source 索引是可达性/关联改进，不能宣称新增了原始信息。每个实验 manifest 明确这一点。

同样，新增此前不可得的单位定义、validation coverage 或证明条件属于信息变化，不能只称为“格式优化”；将事实替换成诊断结论则同时改变解释。一次改变多个因素的方案标为组合包，另做消融后才能分配贡献。

### 8.2 十个开发题与候选信息

| 题目 | 候选补充/派生 | 合格答案与下一步实验 | 应识别的错误 |
| --- | --- | --- | --- |
| SWA 的 `parallel` 是否已经合并提交？ | submit/grid/block 与生成编排对应 | 分清三者，提出保持物理工作不变的提交组织对照 | 仅凭 DSL 关键字判断 |
| RoPE scalar 高来自什么？ | 精确 lowering、axis/mask/dtype/layout、pin | 提出可区分扫描/重排/等待的解释，设计局部对照 | 宣布所有 scatter 都慢 |
| B projection 为什么等其他组？ | 直接依赖、tensor region、数学组关系 | 识别完成边界，提出仅收窄已证独立组依赖 | 无证据删依赖 |
| 请求 stage=2 是否实现了流水？ | 实际 buffers、alias 与 hint | 区分请求与实现；不虚构独立 µs 收益 | 从源码参数认定双缓冲 |
| compressor 谁整体更快、哪里仍弱？ | 同 workload 的阶段映射、完整 bench | 分清局部与整体排序；融合内部不可拆则明示 | 相加重叠 stage span |
| scan-8 可否替代完整扫描？ | position/mapping 合法域和 validation | 条件化接受、补通用反例验证，或拒绝通用替代 | 当前 PASS 等于完全正确 |
| 长序列 projection 的 1 ms 是什么？ | row 分布、launch spread、chunk 关系 | 区分生命周期执行时间与分散启动 | 当作单核 matmul 时间 |
| 更多 blocks / 更高占用是否更好？ | work/grid、无插桩 bench、无收益实验 | 以完整目标判断，允许结论无收益 | 用 occupancy 作为奖励 |
| 两次 capture/不同 shape 能直接比较吗？ | workload、validation、capture identity、objective | 区分 scaling、优化比较和机制证据；拒绝不安全 PMU join | 相同 program/task ID 就配对 |
| 该重复哪个实验、接受哪个结果？ | parent/diff、不变量、typed outcome、条件化摘要 | 排除 precision/compile failure，保留反例，选择区分性实验 | 将 caller win 当作数值验证 |

其中“取全截断证据”作为所有题的访问检查，不作为新增信息的收益。task span、row 生命周期累计 core-µs（含同步与等待）、pipe-active、bench wall time 始终独立标注。

候选信息按组渐进测试：契约/验证 → row 与阶段关系 → source/lowering/work → 独立 PMU 关联 → 实验记忆。顺序可依预试改变；不要求每个算子都获得所有信息。

### 8.3 正向检验后再做移除实验

对胜出的组合逐项移除证据类别，测正确率、错误归因、有效假设与成本的变化。既做“去掉一类”的消融，也做少量“只给最小充分证据”的正向对照，避免高度相关信息互相替代后被错误判为全部无用。

若 CP 与时间窗口都能定位同一问题，应检验移除两者之一、同时移除以及另一类需要完整路径的场景。若 PMU 与 lowering 联合有效，也不能因单独移除 PMU 暂无显著变化就判定所有 PMU 冗余。

无法确定时，结论是“此场景未见增量价值”，不是删除依据。历史案例的已知优化不得直接作为唯一评分答案；允许不同的合法可检验假设。

### 8.4 区分信息不足与变换能力不足

对失败题增加少量诊断条件：先提供相同的、显式的机制事实而不给补丁；必要时再给已验证补丁作为 oracle 对照。若 agent 能定位问题，却无法构造合法表达，说明可能需要 DSL/变换指导或更强搜索，而不是更多 profiling。

oracle 只用于定位失败环节，单列结果；提供机制或补丁后的性能不计为 pfdb 独立带来的优化收益。

## 9. 实验 E3：新反例与未覆盖能力

两例开发集用来找设计错误，不能同时充当泛化证明。分三类扩展，按价值选择最小集合，不做所有 shape/primitive 的笛卡尔积。

| 扩展 | 建议内容 | 谁执行、解决什么问题 |
| --- | --- | --- |
| 两例的未见合法输入 | compressor 的非连续 position、不同合法 mapping/请求、chunk 边界；SWA 不同有效长度/组边界 | 外部 harness 确认 spec 后生成；检验条件化信息能否阻止无效捷径 |
| 机制的反例 | 已知慢 form 以外的合法 scatter/gather form；实际双缓冲可用与不可用；粗/细依赖各有优势的情形 | 先用已有产物，不够再由外部采集；检验经验是否被错误泛化 |
| 低频能力正向场景 | host 延迟、ring heap/scope 峰值、args 物理切片、incore 重叠、rank/clock/epoch 歧义 | 优先用已有真实或明确标注的 synthetic fixture；检验按需发现和完整可达 |

输入扩展必须在原 spec 合法域内；不支持的域只记录为需求问题，不能改 golden 让它成为“反例”。新的 input suite 是新的覆盖，历史通过结果不自动迁移。

在条件允许时，再选择**至少两个不同工作结构的 holdout 算子**：例如归约/访存主导与 GEMM/布局主导各一个。选择规则和预算预先记录，不能只挑新接口表现好的案例。未补齐前，结论仅适用于固定的两个算子和具体起点。

synthetic 用来验证语义、边界与发现路径，不能证明真实加速或代替设备结果。低频能力若没有正向场景，本轮不删除其底层实现。

## 10. 实验 E4：完整优化闭环是否受益

只让离线表现最好的一个候选方案与 A1 基线进入在线预试，控制开销。两组共享外部编译/验证/采集执行器，pfdb 仍只分析执行器产出的工件。

建议预试规模为 **2 算子 × 2 起点（agent/手写）× 3 个匹配 seed × 2 条件 = 24 个会话，即 12 对**。每会话先限制最多 6 个新候选，并统一模型版本、输入/文档、参考可见性、token、墙钟、编译和采集预算；最终数值在预试注册表中冻结。失败候选也消耗预算，不能免费重试。

这是最多 144 个新候选槽位的资源上限示例，不是必须跑满，更不包含未说明的无限设备排队。执行前单列 baseline、validation、PMU 与最终验收的成本；设备池排队时间和有效计算时间分别记录。原样 A0 不参与每轮重跑，只保留 E0 的历史对照。

处理组额外的模型摘要、检索、记忆写入和工具执行都计入资源账本；不强迫两组使用相同的调用次数。建议主动搜索时钟仅暂停由执行器确认的设备池纯排队，模型、工具、编译与实际设备执行均计入；用户实际等待时间另行完整报告。独立设置总等待上限及基础设施失败规则，正式采集前冻结，不能事后按有利结果选择口径。

若要分别评估关联摘要、补充证据和实验记忆，采用逐步增加的独立对照，不把它们一次全部打开后给每项分配收益。实验记忆用同一 parent/历史实验包，测试重复假设、适用域和 prune 后恢复；不能给处理组独占已知最优补丁。

记忆表达对照的两组必须能访问同一批历史尝试事实与完整证据；结构化检索是处理因素。用超过当前 keep-3 工作集的冻结历史单独测 prune 保留能力：若改变了事实的存留，称为保留策略变化，而非仅表达变化。在线轨迹随后自然分叉时，评估的是记忆支持的整体优化策略，不声称全过程历史相同。

### 10.1 正确性与计时

- 两组使用相同、不可变的 reference/comparator/tolerance；记录 implementation 与 validation 的确切绑定，clip/EPS/映射假设不能被忽略。
- 搜索可见验证输入与最终保留的正确性输入分开，后者来自同一预声明合法域，不提供给候选生成阶段；最终确认不能只重复搜索中反复使用的一份 golden。
- 起点在分配实验条件之前先验证；不正确的起点单列，不在看到结果后才剔除某组。
- 搜索中的轮次在进程内采集，使用冻结 golden；不为获得每个 sample 重跑进程。候选变化使产物失效时重新编译，不盲目复用 work dir。
- 候选选择后，按一致 estimator 与配置做独立确认；依项目 acceptance 约定，由外部执行器采集至少三个独立 raw bench strata。当前 `compare --bootstrap` 检查 strata，普通 compare/trial verdict 本身没有通用 acceptance gate；不能将 caller verdict 当作确认。
- 显式使用任务约定的无插桩完整 latency（本两例以 median 为目标）；mean/median、profile makespan、最快 rank/全局窗口不能混用。多 rank 若加入评测，单独固定 aggregation。
- 当前 pfdb bootstrap 输出 mean speedup，不能确认 median 的区间。本计划的 median 确认先由外部执行器按同一 estimator 分析；若开发 median 区间，单列实现与统计测试，不混入 A1。独立 strata 与进程内 rounds 也不能混作同一抽样层次。
- 所有硬件命令在 conda `pypto` 中、经 `npu-run` 分配，逻辑设备 `-d 0`；不绕过共享池或手选物理卡。配对记录平台、时钟/负载与执行顺序，尽量平衡顺序效应。

具体采集遵循[性能测量](performance-tuning.md)、[冻结数据重放](../run-and-validate/save-and-replay.md)和[工件选项](profiling-options.md)。策略口径存在历史差异时，以本次注册的 objective 明示并在实现/文档中统一，不悄悄改变 runtime 指标。

### 10.2 主次指标与失败处理

主结果并列报告：**最终独立验证通过率、会话选定且经独立确认的 incumbent 完整 latency/相对起点 speedup、有效改进会话比例**。不使用搜索中所有候选的最小 noisy latency 作为最终结果。按四个起点分别列出全部配对结果，再报告汇总，避免一个大收益掩盖另一起点失败。

汇总前冻结权重，建议四个固定起点等权，使用归一化的配对 log-speedup，再转换为几何平均效果；不能直接平均不同 workload 的绝对 µs。只有有效测量可进入该性能统计，缺失/失败比例与逐对结果同时报告。

原起点本身验证通过且没有有效改进时，保留原起点、记 1×；最终输出不正确且未合法回退时记失败，不虚构 0 µs，也不从总体中剔除。仅在共同有效会话上计算的 speedup 必须标为条件统计，并同时给出总体失败率。

最终选中的候选未通过独立确认时，退回已验证的前一 incumbent，必要时退回起点，并另外记录确认失败；不能继续引用其搜索中的最快数字。

次指标包括：首次有效收益的时间/候选数、无效候选率、回退、重复假设、错误比较/归因、证据引用可核查率、调用错误与恢复、模型上下文成本、外部采集/编译成本。工具少、token 少、占用高均不是单独的成功条件。

### 10.3 失败、重试与缺失测量

工具误用、处理组独有缺陷、不能恢复的截断、错误候选、候选引发的死锁、agent 超时都是结果并消耗预算，不作为基础设施异常排除。已确认的外部基础设施故障才允许按预注册规则有限重试；保留原诊断，必要时用新进程，不能无限重试直到成功。

持续缺失的最终 latency 标记 missing，说明它对结论的影响；不填 0，不静默删除整对。首次收益时间中，没有收益的会话在统一预算处右删失，报告其数量与预算内分布，不能只平均成功会话。基础设施未决样本可能改变排序时，补充敏感性分析，不假装其具有已确认的性能值。

## 11. 统计、预算与决策门槛

以上 3 seeds、60 次离线尝试和 24 个在线会话是**找设计问题与估计波动的预试规模**，不保证证明收益。根据预试确定主指标、实际可接受的质量损失界限、成本目标、最大追加样本和停止规则，再用未见样本确认。

- 相同题/起点、模型、预算配对；条件顺序随机或平衡，避免会话继承另一组的答案。
- seed 是匹配的重复编号；若模型服务不支持可复现 seed，明确记录，不声称两组使用了相同内部随机数。
- 用同一种评审规则盲评；开放题依据事实、合法域、引用与可检验性评分，不依据是否复述旧方案。模糊题由独立复核裁定，保留分歧记录。
- 保留逐对结果；区间估计注明单位。一个会话中的 100 rounds 不是 100 个独立 agent 样本，多个 shape 也不是多个独立算子。
- 样本推断仅覆盖已测固定任务；只有两个算子族时不宣称总体泛化。跨算子结论需要新增 holdout，而不只是增加同一题 seed。
- 大量消融用于探索；只对预先选择的少数对照做确认。中途查看赢家后追加数据、换阈值或选最好 seed，都必须披露，不能当作预注册验证。

决策采用下表，不预设“所有方案至少提速 5%”这样的统一阈值：

| 决策 | 门槛 |
| --- | --- |
| 修复访问错误 | 确定性复现被修复，公开入口/完整性/只读/回归契约通过；无需先证明优化收益 |
| 压缩默认响应或工具目录 | 预声明的质量非劣界限内，相关成本有可复现下降；关键/低频场景仍能钻取；区间不确定则暂保留 |
| 新增证据/关联 | 针对明确失败类型，有正向/移除对照，并改善决策或完整优化结果；披露额外采集、标注与维护成本 |
| 删除底层能力 | 已有可验证的等价替代、兼容路径与专门正向场景；没有不可替代信息；仅无调用不够 |
| 证据不足 | 保留当前能力或按需入口，记录缺的实验与复审条件；不将无显著差异写成等价 |

错误接受不正确候选、跨 workload 宣称优化、丢失关键证据或破坏 runtime 口径，都是当前实验不能放行的已观测缺陷。有限样本中未观察到这类错误，不是错误率绝对为零的证明。

## 12. 开发工作包与阶段验收

各阶段可形成独立、可审查的小批次；先得到结果，再批准下一项扩张。工作量顺序不等于日历承诺，耗时由预试补充。

| 阶段 | 工作包与范围 | 主要交付 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| M0：基线与盘点 | 版本/客户端审计、manifest、接口台账、10 题与盲评规则；标注缺工件 | 可复查的 A0、数据清单、预试注册表 | 能重放目标问题，答案与 agent 材料隔离，成本上限明确 |
| M1：可靠访问 | 仅 E0 传输修复；建立 A1；同时做不安全比较的回归用例 | 公开入口契约、恢复路径、只读测试 | 取全证据不丢失，错误可恢复；A1 不混入新增语义 |
| M2：最小研究原型 | E1/E2；先静态外部证据包和现有 query 组合；初步正向/移除实验 | 哪些缺口有效、哪些摘要可行、哪些未评估 | 找到值得进入确认的少数方案，而非只有更短响应 |
| M3：反例与闭环确认 | E3/E4；补必要工件；小规模在线预试/选定对照确认 | 决策台账、成本/结果、holdout 局限 | 适用条件明确，质量与收益达到预注册门槛 |
| M4：选定能力开发 | 只实现通过证据支持的条目；一次集中整理默认入口 | 增量实现、迁移、公开手册与示例 | 语义/兼容/agent 回归通过，升级台账更新 |
| M5：发布与复审 | 旧接口弃用期、老库升级、runtime 升级演练 | 发布说明、迁移路径、删除/保留清单 | 可回退，旧事实未被重解释，后续复审有触发器 |

M1 中“不安全比较”的测试先作为当前缺口与后续契约的验收题；真正新增 workload/validation gate 放进信息增补工作包单独评测，不能伪装成纯传输修复。若该 gate 先作为必需正确性修复发布，后续所有对照明确使用这一共同新基线，保留其独立贡献记录。

## 13. 集中清理、兼容与 runtime 升级

集中清理应围绕 M3 的决策台账执行，不在 M0 先删除工具。优先整理默认目录、重复定义、selector、单位/来源和旧文档；只有通过删除门槛的底层代码才移除。

公开兼容要求：CLI/API/MCP 旧名字与参数有明确迁移；schema/tool/analysis 版本各自升级；旧库采用备份/副本演练。旧 evidence、caller verdict、未知 workload/validation 不能在迁移时被升级成新证明。涉及语义变化需要显式 refresh，不能在普通 query 中重算。

按照[集成与升级台账](pfdb-runtime-integration.md)维护：runtime 模块/函数、调用方式、输入/输出口径、函数 hash/revision、兼容错误、guard、复现、测试、退役条件。新派生视图注明是官方分析的投影还是 pfdb 独有的关系/聚合，不复制另一个“更合理”的 CP 算法。

升级演练使用可获得的旧/新工件与已知兼容反例：官方结果 parity、未知格式拒绝、可选模态隔离、快照 stale、显式 refresh、原始 hash 不变、导出/缓存和不支持版本提示。未来上游已修复的缺陷应撤去本地兼容；无法验证新上游时记录未评估，不为完成计划随意更新工具链或修改上游。

弃用默认入口先提供兼容别名/发现路径并跑旧调用测试；变更可逆地发布。旧路径的临时保留不等于长期维护两套分析实现。文档清理时同步手册、示例与 agent 指引，但将“指引文字变化”作为独立变量或固定上下文，避免混淆实验收益。

## 14. 台账、测试与可持续复审

不先建设通用评测平台。复用现有 [golden QA](../../profile_db/tests/golden_qa/test_golden_qa.py)、[MCP session 测试](../../profile_db/tests/test_mcp_server.py)、[runtime 集成测试](../../profile_db/tests/test_runtime_integration.py)、真实工件回归和少量外部执行脚本；新增 agent 轨迹与评审可以先使用版本化 JSON/CSV。

必须分开保存三种记录：

| 记录 | 最小字段 |
| --- | --- |
| 实验注册/结果 | hypothesis、唯一改变、数据权限 digest、模型/预算、case/seed/顺序、metric/门槛、全部结果与失败、偏离协议 |
| 能力/接口决策 | 问题与对象、保留/合并/修复/增补/弃用状态、证据、反例、成本、替代与迁移、未评估范围、负责人/复审点 |
| runtime 集成 | 上游入口、权威定义、pin/hash、兼容 guard/测试/退役条件；链接现有台账，不再维护另一份副本 |

测试分层：确定性事实/契约测试负责不出错；离线 agent 题负责证据使用；在线优化负责实际效果。普通 CI 不绑定付费模型或设备优化会话；模型/硬件评测按版本、成本和变更范围触发，固定快照测试不能代替它。

复审触发器包括：runtime 增加/修复能力、模型版本更换、默认调用通道改变、新算子结构出现、误接受候选、证据续取失败、某项被隐藏能力反复被找回、维护成本显著上升。至少保存先前决定的理由，避免下一轮又凭工具数量重新设计。

## 15. 建议的第一轮执行范围

下一轮先完成 **M0 + M1 + 一组 E1 预试**：

1. 核实工件可用性与实际 MCP/CLI 使用方式，建接口台账和 10 题材料。
2. 修复并验收公开入口、截断恢复和结构化错误，冻结 A1。
3. 在相同证据上，对照现有输出与最小关联摘要，检查质量与成本。
4. 根据失败分类，选最多两类信息缺口进入 E2，而非同时实现六类增强。
5. 形成首份逐项决策表：哪些可以收起，哪些必须保留，哪些需要实验，哪些已有明确修复依据。

此时先不删底层功能、不建通用 source/IR 分析器、不重写全部 MCP、不启动大规模 DSE。只有当小规模实验表明问题确实来自证据缺失或关联不足，再进入相应开发与在线确认。

完成整份计划的标志，不是工具数变少，而是：**每项取舍有可复查的实验与边界，agent 能稳定取得关键证据，并在固定预算下更可靠地产生通过验证的优化结果。**
